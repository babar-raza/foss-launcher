## Objective

Add a `_is_parameter_description()` filter to detect and reject function/method parameter descriptions that leak into claims. These descriptions (e.g., "bold (bool, optional): Sets text bold") are not user-facing claims and pollute the claim pipeline.

## Required spec references

- specs/03_product_facts_and_evidence.md (Claims extraction algorithm)
- specs/04_claims_compiler_truth_lock.md (Claim structure and ID generation)

## Scope

### In scope

- New `_is_parameter_description()` function in `extract_claims.py`
- Integration into `_is_code_like()` as a strong indicator
- Integration into `_is_implementation_detail()` as a strong indicator
- Integration into the main extraction filter chain (both sentence and bullet passes)
- Unit tests for the new filter function

### Out of scope

- Changes to other workers (W4, W5, etc.)
- Changes to claim grouping or classification logic
- Modifying existing filter thresholds

## Inputs

- Raw claim text strings from documentation parsing
- Existing filter chain in `extract_candidate_statements_from_text()`

## Outputs

- New filter function `_is_parameter_description()`
- Updated filter chain rejecting parameter descriptions
- Unit tests validating filter accuracy

## Implementation steps

1. Add `_is_parameter_description(text)` function after `_is_implementation_detail()` (~line 508)
2. Add early return in `_is_code_like()` for parameter descriptions (~line 444)
3. Add early return in `_is_implementation_detail()` for parameter descriptions (~line 500)
4. Add `and not _is_parameter_description(sentence)` to extraction filter at ~line 874
5. Add `and not _is_parameter_description(bullet_text)` to bullet filter at ~line 913
6. Add parametrized unit tests

## Failure modes

1. **False positives on legitimate claims**: Claims like "Convert Excel files to PDF format" could be wrongly filtered. Mitigation: patterns are narrow (require type annotation syntax like `(bool, optional):`) so prose claims won't match.
2. **Regex mismatch on edge cases**: Unusual parameter formats may slip through. Mitigation: parametrized tests cover known patterns; additional patterns can be added incrementally.
3. **Import breakage in tests**: If function is not exported, tests fail. Mitigation: function follows existing underscore-prefix convention and is importable from the module.
