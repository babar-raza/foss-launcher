## Objective

Replace `assign_page_role()` slug-substring matching in W4 with content-signal classification
that uses the available claim kinds to infer the correct page role. Slug matching remains as
a fallback tiebreaker.

**Root cause (RCA H4)**: Pages named `load-introduction` get role `workflow_page` instead of
`comprehensive_guide` because the assignment is purely based on slug substrings. A page with
many `api` claims should become `api_reference` regardless of its slug.

## Implementation steps

1. Read the current `assign_page_role()` to understand its slug-substring logic.
2. Add `available_claims: Optional[List[Dict]] = None` parameter (backwards compatible).
3. When `available_claims` is provided and non-empty, compute:
   ```python
   kind_counts = Counter(c.get("claim_kind", "") for c in available_claims)
   total = len(available_claims)
   ```
4. Apply content-signal rules (these OVERRIDE slug matching if threshold met):
   - `kind_counts["api"] / total >= 0.4` → `api_reference`
   - `kind_counts["workflow"] / total >= 0.4` → `workflow_page`
   - `kind_counts["limitation"] / total >= 0.5` → `troubleshooting`
   - `kind_counts["faq"] / total >= 0.3` OR `slug` contains `faq` → `faq`
   - `kind_counts["feature"] / total >= 0.4` → `feature_showcase`
5. If no content-signal rule fires (ambiguous), fall back to existing slug matching.
6. Add 4 unit tests:
   - `test_api_heavy_claims_gives_api_reference`: 5 api claims → `api_reference` regardless of slug
   - `test_workflow_heavy_claims_gives_workflow_page`
   - `test_slug_fallback_when_claims_ambiguous`: mixed kinds → slug decides
   - `test_no_claims_uses_slug_only`: backwards compat with no claims arg

## Acceptance criteria

- All existing W4 tests still pass
- 4 new tests pass
- `assign_page_role(slug, available_claims=[])` behaves identically to `assign_page_role(slug)`
